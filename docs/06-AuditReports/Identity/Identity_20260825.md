#### CS.06 — Core 抽象の活用

🔴 **Guid.NewGuid() 違反 (4件)**:

| ファイル | 行 | コード |
|:---------|:---|:-------|
| [VKTenantSuspendedEvent.cs](/src/BuildingBlocks/Identity/Tenant/Events/VKTenantSuspendedEvent.cs) | L14 | `public Guid EventId { get; } = Guid.NewGuid();` |
| [VKUserCreatedEvent.cs](/src/BuildingBlocks/Identity/User/Events/VKUserCreatedEvent.cs) | L14 | `public Guid EventId { get; } = Guid.NewGuid();` |
| [VKUserPasswordChangedEvent.cs](/src/BuildingBlocks/Identity/User/Events/VKUserPasswordChangedEvent.cs) | L13 | `public Guid EventId { get; } = Guid.NewGuid();` |
| [VKUserJoinedTenantEvent.cs](/src/BuildingBlocks/Identity/TenantUser/Events/VKUserJoinedTenantEvent.cs) | L15 | `public Guid EventId { get; } = Guid.NewGuid();` |

**対処方針**: Domain Event は `sealed record` でコンストラクタ引数として `EventId` を受け取り、生成元で `IVKGuidGenerator` を使用すべき。ただし `IVKDomainEvent` インターフェースの設計がフレームワークレベルで `Guid.NewGuid()` を前提としている場合は、**Core 側の設計変更が先行する必要がある** (ADR 検討対象)。

🔴 **TimeProvider.System 直接フォールバック (2件)**:

| ファイル | 行 | コード |
|:---------|:---|:-------|
| [VKTenantUser.cs](/src/BuildingBlocks/Identity/TenantUser/Models/VKTenantUser.cs) | L62 | `(timeProvider ?? TimeProvider.System).GetUtcNow()` |
| [VKTenantUser.cs](/src/BuildingBlocks/Identity/TenantUser/Models/VKTenantUser.cs) | L80 | `(timeProvider ?? TimeProvider.System).GetUtcNow()` |

**問題**: `TimeProvider` がオプショナル引数で `null` の場合に `TimeProvider.System` にフォールバックする設計は、テスト時の制御を確保しているが、**CS.06 の「直接使用禁止」原則に違反**。`VKTenant` や `VKUser` は `DateTimeOffset now` を受け取る設計で統一されているため、`VKTenantUser` も同様に `DateTimeOffset now` パラメータに統一すべき。

### 3.6 深度ロジック審査 (Deep Logic & State Evolution)

#### 脳内推演 (Mental Execution)

**成功パス: ユーザー作成 → テナント参加 → ClaimsPrincipal 生成**

1. `VKUser.Create(id, email, displayName, hash, now)` → `VKResult.Success(user)` + `VKUserCreatedEvent` 発行
2. `VKTenantUser.Create(tenantId, userId, role, timeProvider)` → `VKResult.Success(tenantUser)` + `VKUserJoinedTenantEvent` 発行
3. `DefaultUserClaimsPrincipalFactory.CreateAsync(user, tenantId, ct)` →
   - Base claims 生成 (UserId, Email, TenantId)
   - `_tenantUserRepository.FindAsync()` でロール取得
   - ロールを ClaimsPrincipal に追加
   - `VKResult.Success(principal)` 返却

✅ 状態伝播は正常。

**失敗パス: 無効なテナント ID での参加**

1. `VKTenantUser.Create(VKTenantId.Default, userId)` → `VKResult.Failure<VKTenantUser>(VKTenantUserErrors.InvalidTenantId)`

✅ 早期バリデーション + エラー定数。

#### 逻辑死胡同の探索 (Dead Ends)

1. ⚠️ **`VKTenant.Activate()` / `VKTenant.Archive()` が `void` を返却**:
   - [VKTenant.cs:L117-121](/src/BuildingBlocks/Identity/Tenant/Models/VKTenant.cs) — `Activate()` は Suspended → Active だけでなく、**既に Active な状態でも呼び出し可能**で、状態変更なしでも `UpdatedAt` が更新される。
   - [VKTenant.cs:L126-130](/src/BuildingBlocks/Identity/Tenant/Models/VKTenant.cs) — `Archive()` は **既に Archived な状態でも呼び出し可能**で無条件に再設定。
   - **推奨**: `Suspend()` のように `VKResult` を返却し、不正な状態遷移を呼出元に通知すべき。

2. ⚠️ **`VKTenantUser` が `VKEntity` を継承しつつ独自の `_domainEvents` を管理**:
   - [VKTenantUser.cs:L12](/src/BuildingBlocks/Identity/TenantUser/Models/VKTenantUser.cs) — `VKEntity` (基底) に `DomainEvents` 機構が含まれるはずだが、`VKTenantUser` は独自の `List<IVKDomainEvent>` を宣言し、`private void RaiseDomainEvent()` を自前定義。
   - **リスク**: `VKAggregateRoot` の `RaiseDomainEvent()` とは異なる実装パスとなり、EF Core Interceptor によるイベント自動ディスパッチに影響する可能性。
   - **推奨**: `VKTenantUser` を `VKAggregateRoot` に昇格するか、`VKEntity` 基底クラスの DomainEvent 機構を利用すべき。

3. ⚠️ **`DefaultUserContext` の `ClaimsPrincipal` オプショナル引数**:
   - [DefaultUserContext.cs:L15](/src/BuildingBlocks/Identity/Common/Protocols/Internal/DefaultUserContext.cs) — `ClaimsPrincipal? principal = null`
   - [VKIdentityBlock.cs:L27-31](/src/BuildingBlocks/Identity/VKIdentityBlock.cs) — DI 登録時に `principal` が渡されない (`new DefaultUserContext(identityContext)`)
   - **結果**: `DisplayName`, `Email`, `Roles`, `Claims`, `IsInRole()`, `FindClaimValue()` が **常に null / 空** を返却する可能性がある。
   - **リスク**: `IVKUserContext` をリクエストスコープで使用する場合、`HttpContext.User` との統合ポイントが欠落。ASP.NET Core の Middleware / Authentication パイプラインとの接続が必要。

#### 防御的逆向思考 (Destructive Thinking)

🔴 **最大リスク: DefaultUserContext が常に空の Claims を返す可能性**

上記 3. の延長として、`IVKUserContext` を DI から取得するコンシューマは以下の状況に陥る可能性がある：

1. `IVKUserContext.IsAuthenticated` → `false` (principal が null で UserId が Anonymous の場合)
2. `IVKUserContext.Roles` → `[]` (principal が null)
3. `IVKUserContext.Email` → `null` (principal が null)

これは **認証済みユーザーのコンテキストが正しく伝播されない** ことを意味し、Authorization ロジックのバイパスやテナント分離の破綻につながりうる。ただし、これは Identity BuildingBlock が **Domain Layer の抽象のみを提供** し、実際の `ClaimsPrincipal` 統合は Infrastructure Layer (例: `VK.Blocks.Authentication`) で上書き登録される前提の設計思想と考えられる。

## 🛡️ 非機能要件とセキュリティ (Non-Functional Requirements & Security)

- 🔒 **パスワードハッシュの平文保持なし**: `VKUser.PasswordHash` は外部でハッシュ化されたものを受け取る設計。平文パスワードは `IVKPasswordValidator.Validate()` でのみ扱われ、永続化されない。✅
- 🔒 **Email 正規化**: `VKEmail.Create()` で `ToLowerInvariant()` 正規化 + 長さ制限 (256文字)。✅
- 🔒 **アカウントロックアウト**: `VKUser.RecordAccessFailed()` で自動ロックアウト (既定: 5回失敗 → 15分ロック)。✅
- ⚠️ **ロックアウトパラメータのハードコード**: `RecordAccessFailed()` の `maxFailedAttempts` と `lockoutDuration` はメソッド引数のデフォルト値として定義。`VKUserOptions` に `MaxFailedAccessAttempts` と `DefaultLockoutMinutes` が存在するが、**ドメインモデル側で Options を参照していない**。呼出側が Options を参照して引数を渡す必要がある設計。

- ⚠️ **`VKTenantUser` ドメインイベント機構の独自実装**: `VKEntity` 基底を使用しつつ、`_domainEvents` と `RaiseDomainEvent()` を自前で定義。基底クラスの機構と不整合のリスク。

- ⚠️ **`Contracts/` フォルダ名**: `Tenant/Contracts/`, `TenantUser/Contracts/`, `User/Contracts/` — Error 定数のみ格納。VK.Blocks 標準では Feature Slice Root に直接配置するか、Feature 内の型として管理する。ただし `Contracts/` という名前は誤解を招く可能性がある（外部契約・Protobuf 定義と混同）。BB.01 では明示的に禁止されていないが、命名の一貫性のため検討の余地あり。
